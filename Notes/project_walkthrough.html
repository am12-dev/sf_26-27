Orientation

The idea in one page

A DXA scan is the machine that tells you whether someone's bones are thinning. This project asks a simple question: using only what a family doctor already has in the room — a scale, a tape measure, a date of birth, a medication list, a few questions about periods and past broken bones, and routine bloodwork — how well can you guess what the DXA scan would have said?

The reason the question is answerable at all is that a large US government survey, NHANES, did both halves for the same people. It interviewed and examined tens of thousands of Americans and gave many of them a hip DXA scan. So for those people we know both the clinic-style inputs and the scan result. That lets us train a model on the inputs, check it against the scan, and then measure how often the guess is right.

Everything the script does falls into four jobs:

  1. Assemble. Pull fourteen different NHANES questionnaire and lab files across six survey rounds, glue them together by person ID, and narrow to one tightly defined group of women.
  2. Label. Convert each woman's hip bone-density measurement into a T-score, the standardised number clinicians use, and from that produce a yes/no label.
  3. Learn. Train eight different models to predict that label from the 23 clinic inputs, keeping the bone-density columns strictly out of the inputs.
  4. Interrogate. Refuse to take the resulting numbers at face value. Compare against a two-variable formula from 2001, re-run the whole model-selection procedure in a way that cannot flatter itself, and translate the result into the only unit a clinician cares about: how many DXA scans you have to order to find one case.

That fourth job is most of the file's length, and it is the part worth showing a specialist. The headline is not "we got AUC 0.81". The headline is what survived being checked.

Background

Why not just scan everyone

Bone thinning is silent. There is no ache, no symptom, nothing a person notices — right up until a hip or a wrist breaks after a minor fall. By then the damage is done, and a hip fracture at 70 is a life-changing event with real mortality attached.

The test that catches it early is a DXA scan: a low-dose X-ray of the hip and spine that measures bone mineral density — how many grams of mineral are packed into each square centimetre of bone. It works well. The problem is not accuracy, it is reach: a DXA scanner is a fixed, expensive machine, appointments have to be ordered and travelled to, and guidelines in many places only trigger a routine scan at 65. Which means the women in the decade before that — exactly the decade when bone loss accelerates fastest, right after menopause — are largely unscanned unless something else flags them.

So the useful question is not "can a model replace DXA" (it cannot, and this project does not claim it). The useful question is triage: given a room full of 55-year-olds and a limited number of scanner slots, can cheap information rank them well enough that the slots go to the right ones?

What "good enough" means here

A triage tool does not have to be right about individuals. It has to order people better than chance and better than whatever is currently used. The script measures exactly that, and then converts it into scans ordered per case found — see Scans per case found.

The central mechanism

Build the answer key, then hide it

This is the one idea that, if the specialist understands nothing else, they should understand. It is also the thing most likely to go wrong in a project like this, and the script is built around preventing it.

Every woman in the dataset has two kinds of information attached to her. The first kind is the DXA result — the bone density numbers DXXNKBMD (femoral neck) and DXXOFBMD (total hip). The second kind is everything a clinic would know without a scanner. The DXA result is used to write the answer key, and then it is deliberately walled off so that no model can see it as an input. If a bone-density column leaked into the inputs, the model would score near perfectly and mean nothing at all — it would be predicting the scan from the scan.

In code, that wall is the exclude list inside define_features. It names femoral_neck_bmd, total_hip_bmd, t_femoral_neck, t_total_hip, t_score, bone_status, at_risk and osteoporosis — every column that carries any trace of the scan.

A design decision worth knowing about

Feature selection here works by exclusion, not inclusion: the code takes every column in the table and removes the ones on the blocklist. That is convenient — a newly engineered variable is picked up automatically with no extra wiring — but it cuts the other way too. Any future column derived from bone density silently becomes an input unless someone remembers to add it to the list. This is why the script carries a standing leak alarm; see Six ways of cheating, guarded.

Steps 1 – 2

Where the data comes from

NHANES — the National Health and Nutrition Examination Survey — is a continuous US programme run by the CDC. Each two-year "cycle" recruits a fresh nationally representative sample, interviews them at home, then brings them to a mobile examination centre for measurements, bloodwork and, in some cycles, imaging. Crucially, every person gets one ID number, SEQN, and every data file is keyed on it. That is what makes the whole assembly possible.

The script uses six cycles, listed in the CYCLES constant. NHANES tags file names with a letter per cycle (D = 2005–06, E = 2007–08, and so on), except the combined pandemic-era 2017–2020 release which uses a P_ prefix instead. The code derives every filename from that pattern, so adding a seventh cycle is a one-line change plus a folder of CSVs.

Fourteen source modules per cycle, merged on SEQN with a left join anchored on demographics. Missing files are tolerated: load_file returns an empty frame and keep_cols keeps only columns that actually exist, so a cycle that never shipped a module simply contributes nothing rather than crashing the run.

Two files are fetched from the internet, the rest are on disk

The supplement files (DSQTOT_*) and the day-2 diet recalls (DR2TOT_*) are downloaded from wwwn.cdc.gov in NHANES's native SAS transport format and cached locally as CSV. The cache test is "file exists and is bigger than a size floor", which means a truncated half-download gets re-fetched rather than silently used. A failed download is logged and skipped, not fatal. All eleven cache files are committed to the repository, so the pipeline never touches the network again — not even on a fresh clone.

Why day 2 of the diet recall is worth a download

Asking someone what they ate yesterday measures yesterday, not their habitual diet, and the day-to-day scatter is enormous. Feeding a single noisy day into a model systematically drags any real nutrient effect toward zero — the classic regression-dilution problem. Averaging two days does not eliminate it but materially reduces it. On this cohort, 1,369 of the 1,484 women have both days, 90 have one, and 25 have neither.

One quirk that shapes a lot of the code

These CSVs were exported from NHANES with the value labels already applied. So sex is the text "Female", not the number 2; ethnicity is "Non-Hispanic White", not 3; yes/no items are the words "Yes" and "No". That is why the filters accept both forms (isin([2, 2.0, 'Female'])) and why recode_yesno lowercases and matches strings. It also has a quiet consequence: recode_refused, which blanks out the "refused" and "don't know" sentinel codes (7, 9, 77, 99 …), only operates on numeric columns and is therefore a no-op on the label-decoded ones. And because education stays text, the feature builder — which drops all non-numeric columns — silently discards it. Education is collected but never modelled.

The assert is a feature, not a bug

apply_filters ends with assert len(df) == 1484. It exists to make the published cohort tamper-evident: if anyone changes a cycle, an inclusion rule or the DXA requirement, the script stops instead of quietly reporting different results under the same heading. A failing assert means the cohort definition moved — the correct response is to find out why, not to update the number.

Two cycles sit on disk unused, on purpose

data/raw/ also contains 2015–2016 and 2021–2023 data that is deliberately not listed in CYCLES. Adding them would change the cohort and trip the assert. Do not "fix" this without checking why they were excluded.

Step 5

Making the answer key

A raw bone density of 0.72 g/cm² means nothing on its own. The clinical convention is to express it as a T-score: how many standard deviations a person sits above or below the average for a healthy young adult of the same sex. A T-score of 0 is exactly average for a young adult; −1 is one standard deviation below; −2.5 is two and a half.

The script computes it directly, using fixed NHANES III young-adult reference values held as constants:

Femoral neck
reference mean 0.858 g/cm², SD 0.120
Total hip
reference mean 0.942 g/cm², SD 0.122
T-score used
the lower of the two sites, rounded to three decimals

Taking the minimum of the two sites follows clinical practice — a person is classified by their worst measured site, not their average. The rounding to three decimals is not cosmetic: bone density is reported to three decimals, so without rounding, women sitting exactly on a threshold land on either side of it depending on floating-point noise. An earlier version of this code used pd.cut for the classification and put three women on the wrong side of −2.5 for exactly that reason.

From the T-score come two labels and one descriptive category, all derived from the same rounded comparison so they can never disagree with each other:

at_risk — T ≤ −1.0
836 56.3% of the cohort. Osteopenia or worse. This is the primary target.
osteoporosis — T ≤ −2.5
94 6.3%. The WHO diagnostic threshold. A secondary target, evaluated separately.
T-score distribution
−1.08 mean, with SD 1.02 — the cohort average sits right at the osteopenia line.
Read this before quoting the headline number

The primary target is not osteoporosis. It is osteopenia-or-worse, which describes 56.3% of this cohort — more than half. A model that predicts it well is answering "does this woman have any measurable bone loss", not "does this woman have osteoporosis". The osteoporosis-only target has just 94 cases against 23 predictors — about 4 events per predictor, well under the conventional minimum of 10 — so anything estimated on that target alone is fragile. The script evaluates both and reports them side by side rather than picking the flattering one.

The reproductive variables are the most carefully built part of the pipeline

This is where the domain thinking shows, and it is worth walking a specialist through because it reflects how bone loss actually works rather than what was easiest to code.

  • Years since menopause, not just age. Bone loss accelerates through the menopausal transition and the first years after it, then slows. In a 50–65 cohort where menopause timing varies by a decade or more, chronological age is a weak stand-in for where a woman sits on that curve. The script computes years_since_menopause = current age − age at last period (RHQ060), with implausible ages screened out as sentinel codes.
  • Hysterectomy and oophorectomy kept separate. Removing the uterus alone leaves the ovaries producing oestrogen; removing both ovaries cuts it off abruptly. Pooling them into one "surgical menopause" flag buries the variable that should carry the signal. An earlier version of this code did conflate them, and the tell was a near-zero coefficient where a real effect was expected.
  • Why periods stopped. NHANES asks this in RHD042 (2005–2010) and RHD043 (2013 onward). The script coalesces the two and reads the text to separate natural menopause from surgical.
  • Still cycling. RHQ031 asks about any period in the last twelve months; the answer is inverted into postmenopausal.
One variable was built, then deliberately benched

age_at_menopause is computed and saved to the dataset, but excluded from the model. The reason is exact arithmetic: age = age_at_menopause + years_since_menopause, with no slack at all. Keeping all three makes the design rank-deficient — the regression cannot tell which of them owns the effect and splits it across arbitrary coefficients. So it stays in the CSV for descriptive tables and is recovered by subtraction when needed. The script prints a warning saying exactly this, every run.

Three data-quality flags worth raising yourself

phq9_score is 80.4% missing and is nonetheless fed to the model, where the median imputer fills four out of five values with the same number. Its measured contribution is negative — shuffling it improves out-of-fold AUC slightly. It earns its place in neither statistical nor clinical terms.

supp_data_available is not a patient characteristic. It flags whether the woman's survey cycle shipped a supplement file at all — 2005–06 did not, so all 206 of its women are marked unobserved. It is a dataset provenance marker sitting in a clinical feature list. Harmless in practice here (odds ratio 1.00, importance ≈ 0) but it should not be there, and a specialist may well ask.

Three more predictors exceed 15% missingness: alcohol_drinks_day 31.7%, menopause_natural 33.6%, serum_vitd_nmol 23.0%, oophorectomy 17.0%, years_since_menopause 15.8%. All are median-imputed, which is a defensible default but does mean the reported effects for those variables lean partly on fabricated values.

Built into steps 6 – 11

Six ways this could have been wrong, and the guard against each

This section is the strongest thing to bring to a specialist meeting. Most of these are not hypothetical — the code comments record that they were found and fixed, which is a very different and much more credible claim than "we were careful".

1 · Target leakage

Because features are chosen by exclusion, a new column derived from bone density would silently become an input. The standing guard is a coefficient alarm: after fitting, the script checks the largest standardised coefficient against a threshold of 2.0. The largest legitimate one observed is about 0.99 (weight_kg); anything leaking the target would dominate at several times that. This run: largest coefficient 0.990, on weight_kg. Clean.

2 · Clinically backwards effects

A dictionary named EXPECTED_SIGNS records the direction each well-established risk factor should point (weight protective, age harmful, prior fracture harmful, and so on). After fitting, any coefficient pointing the wrong way is printed as a warning. This check is what surfaced the age / age-at-menopause collinearity in the first place. This run flags one: total_vitd_mcg, where higher intake associates with slightly higher risk — a classic reverse-causation pattern, since women told they have thinning bones start taking vitamin D. Worth saying out loud rather than hiding.

3 · Fabricated totals

Calcium intake is food plus pills. The obvious implementation, .add(fill_value=0), would treat a missing supplement figure as a real zero and produce a confident-looking total from half the information. The script uses plain addition so a missing component yields a missing total, and separately distinguishes "this cycle had no supplement file" (genuinely unobserved, left NaN) from "this woman was surveyed and reported no supplements" (a true zero — NHANES codes non-users as blank, not 0). 206 women unobserved; 229 totals left missing.

4 · A variable running under a false name

MCQ160A was previously called rheumatoid_arthritis in this code. It is not rheumatoid-specific — it asks whether a doctor ever mentioned arthritis of any type, and it is positive in 45.8% of this cohort. Rheumatoid arthritis is a genuine FRAX risk factor with a 1–2% prevalence. Under the wrong name, a common, weakly-relevant variable was masquerading as a rare, strongly-relevant one. It is now any_arthritis.

5 · Importance measures that lie

Tree-model importances — Gini importance and split counts — were removed from the reporting. They are unsigned and biased toward continuous variables over binary ones, and here they inverted the real ranking: total_calcium_mg placed 7th despite a completely flat outcome gradient across its quartiles (57.8 / 55.0 / 57.6 / 58.5%), while oophorectomy placed last despite an odds ratio of 1.28. They were replaced with permutation importance — literally: shuffle one column, refit nothing, and measure how much out-of-fold AUC is lost. That is model-agnostic, in the same units for every model, and not biased by variable type.

A file that contradicted this has been removed

feature_weights_matrix.csv, a leftover from a different script, held exactly the tree importance columns that were dropped for being misleading — and looked more authoritative than the correct table because it covered five models. It is gone; see What was removed.

6 · An in-sample score that flatters a forest

A random forest with unrestricted leaves memorises its training rows — its in-sample AUC is close to 1.000 no matter what, and on deliberately shuffled labels this configuration still reaches 0.997. So the train-versus-test gap is meaningless for it. The script enables out-of-bag scoring instead: each row is scored using only the ~37% of trees whose bootstrap sample happened to exclude it. That is the honest in-sample figure for a bagged ensemble, and the leaderboard prints it in its own column with an explicit instruction not to rank models by the train/test gap.

And one thing that was tested rather than assumed

The forest's min_samples_leaf was tuned by nested cross-validation, not chosen by eye. It matters because the intuitive move — raising it to shrink the alarming train/test gap — lowers test AUC monotonically. The gap is the price of the performance, not a defect. Inner CV picked leaf = 1 in 5 of 5 folds for the osteopenia target and 3 of 5 for osteoporosis, lifting test AUC from 0.784 to 0.810 and from 0.829 to 0.835 respectively.

Step 10

The models, in plain terms

Eight models across two families. Every one of them is wrapped in the same three-stage pipeline so that the comparison is fair, and — importantly — so that no preprocessing step ever sees the data it will later be tested on:

  1. Impute — fill each missing value with that column's median.
  2. Scale — recentre every column to mean 0, spread 1, so that a weight in kilograms and a yes/no answer are on comparable footing.
  3. Fit — the model itself.

Because the median and the scaling factors are computed inside each fold, they are learned from the training rows only. Computing them once on the whole dataset up front — a very common mistake — would leak information from the test rows into training.

The five classifiers — trained on the yes/no label

The three regressors — trained on the continuous T-score, never on any label

This arm exists because dichotomising a continuous measurement throws information away. Under the binary label, a woman at T = −2.4 and a woman at T = +0.5 are both simply "negative", which is obviously false. These three models predict the T-score itself, and one fit then serves both clinical cutoffs — you threshold the predicted T-score twice. They are RidgeCV, a random-forest regressor, and a LightGBM regressor.

Why both boosters are deliberately crippled

max_depth=2, num_leaves=4, min_child_samples=50, reg_lambda=50. With 1,484 rows and 23 columns, an unconstrained booster memorises the dataset trivially and reports a fantasy. The heavy regularisation is a decision about the sample size, not a default. Class imbalance is handled per model — class_weight='balanced' for four of them, scale_pos_weight for XGBoost.

How every score is produced: 5-fold cross-validation

Split the 1,484 women into five groups, keeping the proportion of cases equal in each (StratifiedKFold). Train on four, test on the fifth. Rotate five times so every woman is tested exactly once, on a model that never saw her. Average the five results. The random seed is fixed at 42 throughout, so the whole thing reproduces exactly.

How to read this

  • The random forest wins clearly — 0.810 against 0.753 for the linear models. That gap says there is real non-linear or interaction structure that a straight additive model cannot capture.
  • The boosters lose to the forest, which is unusual on tabular data and is a direct consequence of how hard they were regularised. That was the right call for n = 1,484, but it is worth noting that a less-constrained booster was not systematically searched.
  • L2 and elastic net are indistinguishable (identical to three decimals). With 23 well-chosen predictors there is nothing much for the sparsity penalty to remove.
  • The forest is balanced, not skewed — 74.0% sensitivity and 72.8% specificity at the default cutoff. It is not achieving its AUC by flagging everyone.
  • And it is not a fluke of this particular split. When model selection was redone inside each training fold (next section), the forest won in 5 of 5 folds and the nested estimate came out at 0.810 — identical to the leaderboard. For this target the leaderboard was not flattering itself.
The number that gives 0.810 its meaning

By itself, 0.810 is unreadable. The comparison that makes it interpretable is that OST — weight minus age, times 0.2 — scores 0.747 on the same folds. So all 23 variables, the blood work, the diet surveys and the 500-tree forest buy +0.063 AUC over a formula you can do in your head. That is a real gain, and it is also a realistic sense of scale. Always quote the two together.

Five of 23 predictors have a confidence interval that excludes 1

Older age (OR 1.30 per 5 years), being postmenopausal (2.13), any prior fracture (1.72), ever having used oestrogen (0.58, protective) and higher income relative to the poverty line (0.91 per unit, protective). The most instructive row in the table

weight_kg is by far the most predictive single variable — shuffling it costs 0.145 AUC in the logistic model and 0.098 in the forest, five to ten times more than anything else — and yet its odds ratio is reported as non-significant (0.41 – 1.05).

Both statements are true. Weight, BMI and height are three measurements of largely the same physical fact, so the model can shift credit between them almost freely; the confidence interval on any one of them is consequently wide. But collectively they carry the signal, and shuffling weight alone breaks the whole arrangement. The lesson: a wide interval means "we cannot separate this from its neighbours", not "this does not matter." That distinction is exactly why the script reports both columns instead of picking one.

The clinical picture is otherwise entirely conventional — lighter, older, longer-postmenopausal women with a fracture history and no oestrogen exposure are at higher risk. Nothing here contradicts the osteoporosis literature, which is itself a form of validation: a pipeline this complicated rediscovering the textbook is evidence it is wired up correctly.

Step 12

The honesty checks

An AUC of 0.810 sounds respectable. Two questions decide whether it means anything, and roughly half the script's length exists to answer them.

Question one: is it better than a two-variable formula from 2001?

The OST — Osteoporosis Self-assessment Tool — is 0.2 × (weight in kg − age in years). That is the entire model. It was derived by Koh et al. in 2001 from postmenopausal women across eight Asian countries (hence the original name OSTA, “for Asians”), where a variable-selection procedure over the candidate risk factors retained only age and body weight. It has since been externally validated in some nineteen studies, with sensitivity 84–97% and specificity 34–70%, and in non-Asian populations using the same algorithm with locally re-optimised cutoffs. It needs a bathroom scale and a birthdate, and it is the bar any machine-learning model has to clear. The script computes it, plus "weight alone" as an even cruder comparator, and reports every model's AUC relative to OST with a paired bootstrap confidence interval on the difference.

Reporting a bare AUC without that comparison would be uninterpretable. A model that scores 0.81 while OST scores 0.80 has added a great deal of complexity for nothing.

Question two: does picking the winner inflate the winner's score?

Yes, always, and this is the subtlest methodological point in the project. If you fit eight models and report the best one's cross-validated score, that number is biased upward — you chose it because it scored well on those particular rows, and some of that score is luck. The reported best is an upper bound, not an estimate.

The fix is nested cross-validation: move the act of choosing inside the training data, so that no test row is ever involved in selecting the model that will be scored on it.

Both the at_risk and the osteoporosis targets go through this whole apparatus, and the script ends with an explicit verdict for each — "beats OST" only if the nested 95% confidence interval on the difference excludes zero. Its own closing words: "the nested row is the defensible number."

Why this is a good result to present, not a bad one

A project that reported "AUC 0.833 for osteoporosis detection" would be reporting a number its own data does not support. This one built the machinery to catch that, ran it, and printed the uncomfortable verdict itself. Bringing a specialist a result that says "this half works, this half we cannot yet claim" is far more credible than two impressive numbers — and it points straight at what the next round of work needs: more osteoporosis cases.

A neat side result on regularisation

The leaf-size sweep confirms the counterintuitive claim in the code comments. For osteopenia, per-fold AUC falls monotonically as leaves get larger: 0.810 at leaf = 1, then 0.798, 0.784, 0.775, 0.770, 0.762 at leaf = 50. Every attempt to "fix" the forest's perfect training score by constraining it makes real performance worse. The gap is the price of the performance.

A technical detail that keeps the nested number honest

Different outer folds can select different winners, and a classifier's output (a probability between 0 and 1) is not on the same scale as a regressor's output (a negated T-score, roughly −1 to 4). Pooling those raw values into a single AUC would corrupt the ordering and deflate the result. So rank_within_folds converts every score to a within-fold percentile before pooling. AUC only uses order, so this changes no within-fold comparison — and it is applied identically to both the model and the OST baseline, keeping the contrast paired.

Steps 12 – 13

Scans per case found

AUC is not a clinical unit. No one orders 0.81 of a scan. The last part of the script translates the model into the decision a clinician actually makes, in two complementary ways.

referral_table — the screening cost table

For each cutoff it reports: how many DXA scans get ordered, how many cases that finds, how many are missed, the positive predictive value, and scans ordered per case found. The last row is always "scan all" — 100% sensitivity at maximum cost — so the trade-off is visible against the alternative of not triaging at all.

optimize_for_early_detection — the sensitivity-first sweep

A separate, deliberately different forest: shallower (max_depth=6), larger leaves (min_samples_leaf=15), and weighted 3:1 in favour of catching cases. It is wrapped in CalibratedClassifierCV with sigmoid calibration, which matters: an uncalibrated forest's "0.30" is not a real 30% probability, and if you are going to set a clinical threshold at 0.30 then the number behind it had better mean something. The sweep then walks the cutoff down from 0.50 to 0.25, targeting ≥ 80% sensitivity, and reports missed cases and scans flagged at each step.

Why lowering the threshold is the whole point

The default 0.5 cutoff treats a missed case and a false alarm as equally bad. In screening they are not remotely equal: a false alarm costs one unnecessary scan, a missed case costs a hip fracture five years later. Both of these functions exist to let a clinician choose that trade-off explicitly rather than inherit a software default.

Do not put these two tables on the same slide without this caveat

They look contradictory and are not. They differ in two ways at once:

  • Different models. The referral table uses the leaderboard-winning forest (unrestricted leaves, AUC 0.810). The sweep uses the separate shallow, calibrated, 3:1-weighted forest — which scores 0.764 ROC-AUC, noticeably worse, because it was built for calibrated probabilities rather than maximum ranking.
  • Different meaning of "cutoff". The referral table is called with as_quantile=True, so "0.50" means flag the top 50% of scores. In the sweep, "≥ 0.50" means a predicted probability of 0.50. The same printed number denotes two different things.

Why the coefficient file is explicitly not for presentation

Its job is to catch bugs, not to describe biology. Standardised coefficients are in units of "per one standard deviation of this dataset", which is not a clinical unit; and because weight, BMI and height share information, the individual numbers shift around between them. It is a smoke alarm — a coefficient above 2.0 means a leak, a coefficient with the wrong sign means a wiring error. Both are useful to you. Neither belongs in front of a clinician, who would reasonably read −0.99 for weight as a finding rather than a diagnostic. The script now says so in its own output, on the line after it writes the file.

Both problems from the first draft of this document are now closed

The presentable results are on disk. The leaderboard, the OST/nested verdict, the referral tables and the threshold sweep are written as CSVs rather than printed and lost. The verdict file in particular is the one to open first: it is a two-row summary of the entire project.

The folder is unambiguous. Thirteen stale files are gone, and the nine that remain carry an explicit tier. A colleague opening outputs/ can now tell the clinical table from the diagnostic one without reading the source.

One trap survives by necessity — it is now labelled rather than removed

referral_table.csv and threshold_sweep.csv both have a cutoff column containing 0.50, 0.40, 0.35, 0.30, 0.25 — and they mean different things, for different models. The first is a top fraction of the score distribution from the leaderboard forest (AUC 0.810); the second is a predicted probability from the calibrated forest (AUC 0.764). The column names and the per-row model labels now make this visible in the files themselves, but the two tables still must not be merged or plotted on shared axes.

One genuine gap this opened, worth knowing about

Deleting calibration_curve.png leaves the project with no calibration figure, and step 13 depends on calibrated probabilities being trustworthy — that is the whole reason it wraps the forest in CalibratedClassifierCV. The numbers are sound (the sweep reports PR-AUC alongside ROC-AUC), but if a specialist asks "are these probabilities real?", the honest answer today is that the sweep table implies it and no plot demonstrates it. Regenerating a calibration curve from this script is the obvious next addition.

The rule that now holds

Everything in outputs/ is produced by one run of one script, is labelled Present, Methods or Diagnostic as it is written, and traces to a line number. Nothing in there is a mystery, and nothing in there contradicts the method it sits beside.

outputs/run_log.txt is the exception and is yours, not the script's — a manual capture of a full run's stdout. Useful as a complete audit trail; just note it is a snapshot, not a regenerated artifact, so it will silently go stale.

For the meeting

The four-sentence version

Using six rounds of NHANES data, we assembled 1,484 non-Hispanic White women aged 50–65 who received a hip DXA scan, and trained models to predict their bone-density category from clinic-available information alone, with every trace of the scan excluded from the inputs. A random forest reaches a cross-validated AUC of 0.810 for detecting osteopenia or worse, at 74% sensitivity and 73% specificity. Tested honestly — with model selection moved inside each training fold — that beats the OST formula by 0.063 AUC with a confidence interval clear of zero, and it beats it in every fold. For osteoporosis specifically we cannot make that claim: the apparent advantage shrinks from +0.060 to +0.031 once selection bias is removed, and the interval crosses zero, because there are only 94 cases.

Questions to expect, and the honest answers

Your outcome is bone density, not fractures. So what?
Correct, and it is the biggest limitation. NHANES is cross-sectional — everyone is measured once, with no follow-up — so no fracture outcome is available. This predicts a test result, not an event. It is a triage tool for who should get scanned, not a fracture-risk calculator like FRAX, and it should not be compared to one.
56% prevalence? That is nothing like my clinic.
Also correct, and it matters for the numbers. The target is osteopenia-or-worse, which is genuinely common in this age group, but NHANES is a survey sample, not a referral population. Sensitivity and specificity travel across settings; positive predictive value and scans-per-case do not. Any referral table would need recalculating against local prevalence.
Why only white women 50–65?
To keep the statistical power focused. With 1,484 people, modelling sex, ethnicity and a wide age range as well would spread the data too thin. The cost is that nothing here generalises outside that group, and the same pipeline would have to be re-run and re-validated for any other population. The narrow cohort is a starting point, not a claim of generality.
How much of this is self-reported?
Most of the questionnaire variables — prior fractures, steroid use, menopause history, smoking, alcohol. Weight, height and blood 25(OH)D are directly measured. Self-report attenuates real effects, which biases toward under-stating the model's ceiling rather than overstating it.
Has it been tested outside this dataset?
No. Everything here is internal cross-validation on one dataset. The nested-CV result is the closest honest estimate of out-of-sample behaviour, but external validation on a genuine clinic cohort has not been done and is the obvious next step.
What about calcium and vitamin D? Surely those matter for bone density.
They are measured here about as carefully as this dataset allows — supplement intake added to a two-day dietary average, plus a blood 25(OH)D level — and none of the three shows an association with bone density in this cohort. Calcium OR 1.01 (0.90–1.11), vitamin D intake OR 1.01 (0.99–1.08), serum 25(OH)D OR 0.94 (0.82–1.05); all three intervals include 1. Removing all of them from the model changes cross-validated AUC by +0.004, well inside the fold-to-fold variation of ±0.027 — statistically indistinguishable from no change.

This is a null result, not a missing measurement, and the distinction matters: the careful measurement is precisely what licenses the statement. It is also consistent with the reverse causation below. What it does not license is any claim about supplementation changing bone density — that needs a trial, not a cross-sectional survey.
Why is vitamin D intake pointing the wrong way?
The script flags it automatically. Higher supplemental vitamin D associates with slightly higher risk, which is almost certainly reverse causation — women who have been told their bones are thinning start taking supplements. It is a good illustration of why a cross-sectional design cannot settle questions about treatment effects.
Which single number should I trust?
The nested cross-validated difference against OST: +0.063 [+0.046, +0.082] for osteopenia-or-worse, and +0.031 [−0.013, +0.077] for osteoporosis. Not the leaderboard's 0.810 and 0.833 — those were chosen partly because they looked good on those particular rows. For osteopenia the two agree exactly, which is itself reassuring. For osteoporosis they do not, and the nested one is right.
Is a two-variable formula really the benchmark?
It is the right benchmark precisely because it is so cheap: weight minus age, times 0.2. It scores 0.747 here. Any model that needs 23 variables, blood work and a diet survey has to justify itself against that, and for osteoporosis specifically it currently cannot. If a specialist prefers FRAX as the comparator, that is a fair challenge — FRAX is not implemented here, and it predicts fracture rather than density, so it is not directly substitutable.

Two things to ask them for

  1. The cutoff. The referral tables lay out the trade-off, but the acceptable number of missed cases per hundred, and the acceptable number of scans per case found, is a clinical judgement — not one to make from the code.
  2. Missing risk factors. Parental hip fracture, height loss, current smoking intensity and weight change since 40 are all established and all absent here. If any are routinely in their notes, they are candidates for the next iteration.
The obvious objection

Why the benchmark is OST and not FRAX

FRAX runs on much the same primary-care inputs — age, sex, weight, height, prior fracture, steroids, smoking, alcohol — and can be computed without a DXA. So the first question any specialist will ask is why this project measures itself against a two-variable formula from 2001 instead of the tool everybody actually uses.

The answer is that they predict different things, for different decisions, at different points in the care pathway.

FRAX answers “should I treat?”; this model answers “should I scan?” Those are sequential decisions, not competing ones.

Two reasons FRAX could not be the comparator here

  • The outcome does not match. OST was built to predict low BMD. FRAX was built to predict fractures. Benchmarking a BMD-prediction model against FRAX would measure it against a tool designed for a different target — and would flatter or punish it for reasons that have nothing to do with how well it does its own job.
  • NHANES cannot support it anyway. FRAX requires parental hip fracture, which NHANES does not record, and validating against FRAX’s actual outcome would require fracture follow-up, which a cross-sectional survey has none of. Neither the input nor the outcome is available.

And FRAX is known to be weak at this particular job

This is the part worth bringing to the meeting, because it is not a matter of opinion — using FRAX-without-BMD to decide who needs a DXA has been tested directly, and in this project’s exact age band it performs poorly.

FRAX-without-BMD is not a proxy for a T-score, and the literature is explicit that its performance target should be fracture risk rather than BMD classification.
The strongest framing: complementary, not competing

FRAX performs better with a BMD value than without one. So a tool that improves who gets scanned improves the quality of the input FRAX depends on downstream. That is a coherent clinical story and it requires no claim of superiority over FRAX at all — which is just as well, because this project never tested fracture prediction and could not have.

Say this before anyone else does

More than 75% of people who sustain a fragility fracture do not meet the T ≤ −2.5 threshold. Bone density is an imperfect surrogate for the thing anyone actually cares about, so predicting it well bounds what this model can ever claim. That is an argument for eventually predicting fractures rather than densities — which needs a prospective cohort this project does not have, and is the single best reason to seek a clinical collaborator.
